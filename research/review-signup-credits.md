# Independent technical review: Clerk + Stripe + signup + credits

## VERDICT

**FAIL — blockers.** The checked-in UI is deployed, but `omo.best` is running the placeholder/local demo configuration, its same-origin `/api/*` routes return Vercel 404s, and the fallback demo API hostname does not resolve. Enabling a real Clerk key would not recover signup because the hard-coded Clerk SDK hostname is NXDOMAIN. Separately, the worker is unsafe to expose: it trusts an unauthenticated client-supplied `user_id`, allowing account disclosure/debit, arbitrary $5 account creation, and paid-run rate-limit bypass.

Review basis: fresh `main`/`origin/main` at `ba83b07`, implementation commit `bf9e22e`, source inspection, the three requested suites, local browser checks at `http://localhost:8941`, and live browser/curl checks against `https://omo.best` on 2026-08-11.

## VERIFIED

- The implementation commit `bf9e22e` and all listed changed/new files are tracked; `HEAD` and `origin/main` both point to `ba83b07`. The worktree was clean before creating this report.
- Live `signup.html`, `clerk.js`, `dashboard.html`, `stripe.js`, `index.html`, `api.html`, and even the statically served `deploy/worker.js` matched the local files byte-for-byte. This verifies artifact upload, not an executable worker route.
- All favicon/manifest assets tested (`favicon.svg`, `.ico`, 16/32/192/512 PNGs, Apple touch icon, and `site.webmanifest`) returned HTTP 200 with appropriate content types. The signup page’s referenced icon files resolve.
- The $5 constant is consistent in `site/deploy/balance.mjs:14`, signup copy (`site/signup.html:165`), dashboard grant/balance copy (`site/dashboard.html:544-551`), API billing copy (`site/api.html:228`), and worker grant default (`site/deploy/worker.js:669-672`). The stale setup/docs exceptions are reported above.
- `user.created` calls `getUserRecord`, and creation is idempotent at the user row/ledger level. Lazy `/api/me` provisioning and a later webhook do not double-grant (`site/deploy/worker.js:601-613`, `site/deploy/worker.js:703-731`). Security of the caller is not verified.
- Demo mode creates a local user and starts a clean browser profile at $5. A known slug survived storefront → signup → dashboard and opened the correct dialog on both localhost and `omo.best`. An unknown slug showed the graceful “no longer in the catalogue” notice (`site/deploy/worker.js` was not involved).
- The dashboard chips are `$20/$50/$100/$200`. Local browser checks confirmed `$4` and `$5.001` are rejected without changing balance, `$5.01` is accepted and rounded/displayed correctly, and choosing the `$50` chip clears custom input and adds exactly `$50` in mock mode.
- In configured Stripe mode, `stripe.js` does not fall back to local credit after a failed server call; it reports an error. LocalStorage manipulation changes only client/mock display and does not directly invoke server `creditTopup`. The current production configuration nevertheless deliberately selects that mock path.
- Stripe webhook verification uses the raw request body, HMAC-SHA256, timing-safe comparison, and a ±5-minute tolerance. Fulfillment requires `checkout.session.completed`, `payment_status === "paid"`, matching metadata/total cents, and an event ID. Neon idempotency is enforced by both event and Checkout Session unique keys inside a transaction (`site/deploy/worker.js:536-568`, `site/deploy/worker.js:882-929`).
- The Neon pool is created at module scope, reused while the URL is unchanged, capped at four connections, and releases checked-out clients. Neon debit, refund, and top-up balance changes use atomic SQL updates inside transactions. Concurrent top-up versus debit does not have a lost-update bug on the Neon path (`site/deploy/worker.js:621-658`, `site/deploy/worker.js:767-929`).
- Unknown `?open=<slug>` values are handled without an exception and produce a visible catalogue notice (`site/dashboard.html:833-839`).
- Mock-mode slug preservation works through `redirectToSignup`, `dashboardRedirect`, `signUpAndRedirect`, and dashboard lookup (`site/index.html:1347-1350`; `site/clerk.js:90-104`; `site/clerk.js:159-170`; `site/dashboard.html:833-839`). The real Clerk redirect options preserve the same absolute target in source, but real mode could not be executed because of the deployment/CDN blockers above.
