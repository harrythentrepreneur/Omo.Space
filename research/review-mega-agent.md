# Independent technical review: mega-agent blueprint

## VERDICT: FAIL

**Fail means “not implementation-ready,” not “discard the architecture.”** The control-plane builder/data-plane runtime split is sound, and the blueprint correctly preserves Modal as the universal execution plane, the Worker as the only public gateway, immutable per-listing releases, server-owned choices, and the guarded 80% pricing formula. However, `scripts/mega-build.sh -> 12 gates -> LIVE` cannot be implemented against the current repository. The document calls the autopilot and paid platform “existing” even though they are design documents, and it postpones most of Round 5 Steps 1–8 into its own Step 6. There is no public `/v1/runs`, authenticated tenant model, complete Neon/D1 schema, atomic run/reservation/outbox transaction, R2 artifact plane, signed Worker↔Modal protocol, compiler, registry, release controller, cost telemetry, or QA evidence system.

The practical critical path is:

1. ratify D1 versus Neon as the paid system of record and freeze the transactional/state contracts;
2. close the unsafe demo route and build the authenticated `/v1/runs` gateway, migrations, run/ledger/outbox/reconciliation, and R2 plane;
3. freeze the container spec, adapter ABI, registries, hash rules, compiler/runtime, and release controller;
4. prove one manually promoted pure-LLM vertical slice, then one async provider slice and one real GPU/media slice;
5. only then build the general extractor/research/refinement agent and run the four exact acceptance projects.

The four-project production-canary battery is an epic-level exit criterion, not a credible Milestone 1. The exact source packets are not in the repository, and two project names are explicitly ambiguous.

## CONTRADICTION LIST VS ROUND 5 / CONTAINER PLAN

1. **Paid system of record — unresolved, material contradiction.** Blueprint chooses Neon (`research/mega-agent-blueprint.md:10,151-152,630`); Round 5 repeatedly mandates D1 (`research/modal-optimization/round-5.md:19,33,71,118,170,176`). The current demo’s Neon preference does not by itself supersede the final architecture. This requires an ADR, not a parenthetical reconciliation.

2. **Implementation order — direct contradiction.** Round 5 Steps 1–3 close `/api/run`, install migrations, and build the gateway before the spec/compiler (`research/modal-optimization/round-5.md:288-294`). Blueprint Steps 1–5 build the agent/compiler/tester and leave the gateway, database, signed dispatch, artifacts, registry and billing integration to Step 6 (`research/mega-agent-blueprint.md:640-703`). Blueprint Step 5’s crash/replay criteria cannot run in that order.

3. **“Existing autopilot” — contradicts source status.** The container plan says it is analysis only (`research/modal-container-plan.md:3`) and describes future files/commands (`:460-467,755-782,1036-1039`). Round 5 labels the compiler/controller new work (`research/modal-optimization/round-5.md:369-380`). The repository has no autopilot implementation.

4. **Reference shipment sequence — blueprint discards the final de-risking ladder.** Round 5 requires a pure-LLM release first, HeyGen async second, and real GPU only after offline benchmark (`research/modal-optimization/round-5.md:298-301`). Blueprint makes four unrelated production canaries the first mega-agent milestone (`research/mega-agent-blueprint.md:46,701-712`) without first proving those three reusable lanes.

5. **Promotion policy — ambiguous conflict.** Round 5 disables automated promotion until one manual LLM, remote-provider and GPU release each has 30 clean days (`research/modal-optimization/round-5.md:301`). Blueprint repeats that invariant (`research/mega-agent-blueprint.md:634`) but also lets a non-interactive staging command progress to public `LIVE` (`:400-421,438`). A human approval record may authorize a controller action, but the document must explicitly separate manual approval from automated promotion.

6. **Release-hash inputs — incomplete internal statement versus Round 5.** Blueprint `:283` describes generated outputs as a product of only spec + prompts + schemas + compiler version, whereas Round 5 requires source, capabilities, runtime, lock, base image, adapter/model/weight, secret binding, resources and cost policy (`research/modal-optimization/round-5.md:159`). Blueprint later lists more inputs at `:622`, leaving the actual hash contract contradictory.

7. **Original container-plan direct Modal API — intentionally and correctly superseded.** The original plan exposed Modal call IDs and direct submit/poll URLs (`research/modal-container-plan.md:15-19,363-458,755-808`). Round 5 explicitly removes buyer-visible Modal identifiers and makes the Worker the only gateway (`research/modal-optimization/round-5.md:19-21,64-110`).
